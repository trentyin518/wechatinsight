# Proposal

## Why

我们需要一个面向微信公众号的数据分析平台（对标西瓜数据核心能力），为内容创作者、自媒体运营者和营销机构提供公众号搜索、历史文章与互动指标查询。设计文档明确要求「数据真实性优先于功能数量」，因此第一版必须先打通一条**可验证的最小数据闭环**：从第三方数据源获取真实数据、落库为可追溯的历史快照、再通过自有 API 与前端呈现，避免在数据源未验证前投入大额采集或复杂功能。

## What Changes

本项目当前为空仓库（仅有 OpenSpec 脚手架）。本变更构建第一版最小闭环，对应设计文档阶段 0～4 与任务清单 T01～T18（P0）：

- 搭建同一 Git 仓库下的 `frontend/`（Next.js + TypeScript）、`backend/`（Python + FastAPI）、`worker/`（Python 采集）三段式骨架，配置 PostgreSQL 与 Alembic 迁移，提供 `/health` 健康检查。
- 定义统一的 `WeChatProvider` 接口，并为第一个验证通过的数据源实现适配器；业务层不直接依赖任何供应商 SDK。
- 建立统一数据模型：公众号、文章、文章指标历史快照、供应商映射、数据源配置、采集任务、API 调用与成本日志。`null` 表示「未获取」，不等于 `0`；指标按时间快照保存，不覆盖。
- 实现 P0 查询 API：公众号搜索、公众号详情、历史文章列表、文章详情、文章指标历史，统一分页、错误结构与数据来源/更新时间标注。
- 实现 MVP 页面：首页搜索、公众号搜索结果页、公众号详情页、文章详情页，明确展示数据来源与采集时间，缺失数据不伪造。
- 实现独立 Python Worker 与定时调度：账号资料同步、历史文章同步、文章指标更新三类任务，支持重试、幂等、分页游标保存、调用量与预估成本记录。
- 打通前后端部署骨架（Vercel + 云服务器），密钥仅存服务端。

**不在本变更范围**（后续独立变更）：排行榜、趋势分析、账号对比、关键词/疑似推广识别、用户注册登录、收藏、监控、会员与支付、多数据源并行、Redis/Celery。设计文档阶段 0 的数据源验证是编码前的**前置条件**：必须至少有一个数据源通过能力、成本与授权验证后，才进入适配器实现。

## Capabilities

### New Capabilities

- `data-providers`: 统一数据源抽象与适配器契约——标准化公众号/文章/指标的数据结构、字段映射、账号与文章去重、限流与重试、供应商映射。
- `wechat-accounts`: 公众号搜索与详情能力——基于本地库的搜索、详情展示、数据来源与更新时间标注、受控的冷启动查询。
- `wechat-articles`: 文章与互动指标能力——历史文章列表、文章详情、按时间保留的指标历史快照与观测变化。
- `data-ingestion`: 后台数据采集能力——三类同步任务、调度策略、任务状态机、重试/幂等/游标、调用量与预估成本记录、数据分层更新。
- `query-api`: 对外查询 API 契约——版本化路由、统一分页、稳定错误信封、健康检查、数据缺失与数据源不可用降级、限流与额度。
- `web-app`: 前端查询体验——首页搜索、搜索结果、公众号详情、文章详情，数据溯源展示与空/错误状态。

## Impact

- **新增项目结构**：`frontend/`、`backend/`、`worker/`、`docs/`、根级 `.gitignore` 与 `README.md`。
- **新增依赖**：Next.js/TypeScript；FastAPI、SQLAlchemy、Alembic、APScheduler、httpx（后端/Worker）；PostgreSQL 驱动。
- **新增数据库表**：`wechat_accounts`、`wechat_articles`、`article_metrics`、`provider_account_mappings`、`data_providers`、`sync_jobs`、`api_usage_logs`（用户/收藏/监控/会员相关表留待后续变更）。
- **外部依赖**：至少一个第三方微信公众号数据 API（Qovia / 极媒 / 竹简之一），需先完成数据源验证与商业授权确认；缺少可用数据源时本变更阻塞。
- **运维**：环境变量管理第三方密钥，禁止前端暴露；前端 Vercel、后端与 Worker 共用云服务器；每日数据库备份。
- **合规**：仅接入授权数据源，区分「第三方原始数据 / 平台计算指标 / 模型推断」，标注来源与更新时间。
